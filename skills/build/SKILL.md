# Build and verification

You work autonomously and do not dispatch sub-agents. Make focused code changes when the task requires them, then verify the result. Never commit, push, switch branches, merge, or change git state.

Read `CODESTYLE.md`, `AGENTS.md`, and the relevant files under `docs/`.

## Inputs

- The task or plan, with the files that are expected to change.
- The verification scope: focused paths for a small change, the whole project for a cross-cutting one.

## Process

1. Read the task, the plan, and the affected modules before editing.
2. Follow the project architecture: FSD layers, public API through `index.ts`, `_ui/` is private, relative imports inside `entities` and `features`, features do not call the API of other features, and the root element of a component is `ComponentWrapper`. Details: `architecture`.
3. Error handling: `parseApiError` → `showToast.error` → `throwException`.
4. State: RTK Query for server data, `sessionState.use*()` for stable UI selections, `pageNavigationState.use*()` for navigation, local `useState` for local UI.
5. Do not leave placeholders or stubs such as `// TODO`.
6. Never edit `.env.development.local` or any other `.env*`/`*.local` file. The development env file is generated by `scripts/gen_env_*.js`.
7. Do not start long-running dev servers (`pnpm run-*`).
8. Run the verification matrix below.
9. If the task asks for a plan, write it to `<project root>/.opencode/plans/<task-slug>.md` — the project's plans folder shared with `plan`; never to a global directory (`~/.opencode/plan`, `~/.config/opencode/**`).

## Verification matrix

Two blocks: **iteration** (fast feedback while editing) and **final verification** (once, at the task/plan close-out).

| Change                                            | Iteration                                                                                                 | Final verification           |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ---------------------------- |
| Any `src/**` change                               | `pnpm exec vitest run <all affected paths, one call>` → `pnpm lint` → `pnpm typecheck`                     | `pnpm build` → `pnpm test`   |
| Shared API, RTK Query endpoints, entities helpers | same iteration row (focused Vitest for the module, one call)                                               | `pnpm build` → `pnpm test`   |
| Docs, skills, agent config only                   | `pnpm typecheck`                                                                                           | — (CI covers the full suite) |
| Build configuration, env generators, CI           | —                                                                                                          | `pnpm build` → `pnpm test`   |
| Nothing changed in `src/`                         | `pnpm typecheck`                                                                                           | —                            |

Rules:

- A command counts as passed only with exit code 0. Paste the exact commands and their results into the report.
- `pnpm build` already runs `pnpm typecheck`: never run a standalone typecheck and `pnpm build` in the same row. `pnpm build` and the full `pnpm test` belong to the final verification block only — never to the iteration.
- **One run — one result.** The truncated preview hides test-failure summaries (they sit at the end of the output), so build the filter into the first and only run: `… 2>&1 | tail -80` or `… | grep -E '<failure markers>'` (`tail *`/`grep *`/`head *` are allow-listed, the scanner passes these compound calls). For a deep dive use `pnpm exec vitest run <paths> --reporter=json --outputFile=.tmp/<slug>.json` (one call, known path) and inspect the file with `rg`/`cat`. Re-running the same command just to change the output filter is forbidden.
- **Batch Vitest paths.** Pass all affected test paths in a single `pnpm exec vitest run` call (one cold start), never one file per run, and never several concurrent runs of the same tests.
- If a check fails, fix the cause and rerun the failed command and the rest of its row — commands that already passed are not repeated.

## Live check (optional browser verification)

When the change affects UI and the dev server is already running, verify the result in real Chrome via the MCP server `browser` tools. Allowed tools: `browser_browser_navigate`, `browser_browser_navigate_back`, `browser_browser_snapshot`, `browser_browser_find`, `browser_browser_click`, `browser_browser_hover`, `browser_browser_type`, `browser_browser_press_key`, `browser_browser_select_option`, `browser_browser_fill_form`, `browser_browser_wait_for`, `browser_browser_console_messages`, `browser_browser_network_requests`, `browser_browser_network_request`, `browser_browser_tabs`.

Preconditions:

- The user has started the dev server (`pnpm run-dev`, Vite on `http://localhost:3000`, strictPort). Never start it yourself — Process rule 7 stands.
- The Keycloak session in the persistent Chrome profile is active (one-time manual login by the user). If the Keycloak login page opens, ask the user to log in manually in the headed Chrome window; never enter credentials yourself.
- If the dev server is not running, skip the live check silently — it is neither `BLOCKED` nor a failure.

Steps:

1. `browser_browser_navigate` → the target URL (default `http://localhost:3000`).
2. `browser_browser_snapshot` (limit `depth` for large pages) or `browser_browser_find` to locate the expected elements; interact via refs from the snapshot.
3. `browser_browser_console_messages`; use `browser_browser_network_requests` when the change touches API calls.

Success criteria:

- The expected elements are present in the snapshot.
- No **new** console errors relative to the baseline: the React DevTools INFO banner; during session start/expiry — pairs of `GET .../auth/me 401` + `Ошибка запроса к API GET auth/me 401`. MUI/deck.gl dev warnings are acceptable.

Token warning: one snapshot per check — do not re-request a snapshot without page changes; prefer `browser_browser_find` to locate elements.

## Output

`DONE` or `BLOCKED` with a short summary of the changes, the exact commands run, and their results. Answer the user in Russian.

## BLOCKED

- A verification command fails and the cause is outside the allowed edit scope.
- The task requires editing `.env*` or `*.local`.
- A long-running dev server is required to proceed.
- The repository state contradicts the plan (for example, unrelated dirty files).

## Out of scope

Sub-agents, commits, pushes, branch switches, merges, MR creation, deploys, and dev servers. Architecture rules: `architecture`; test rules: `testing`.
